# 《群岛回波 / Echoes of the Archipelago》详细开发计划

状态：执行草案，2026-09-27。依据 `plan.md`、`plan-code.md` 和 `plan-legacy.md` 编写。本文规定阶段、依赖、交付物和验收；未决玩法规则仍以 `plan.md` 第 7 节为准。

## 1. 交付目标和工作方式

项目使用 Godot 4.x，Windows 桌面优先，GDScript 为主。Godot 工程位于仓库根目录，设计文档和开发规范位于 `docs/` 与根目录。先完成单关海空闭环，再扩展系统与内容。

每个工作包都按 **规则/输入 → 实现 → 可观察反馈 → 验证 → 文档更新** 交付。进入下一阶段以验收结果为准，不能只看功能数量或日历时间。`plan-code.md` 的周期为粗估，默认不包含大量美术、剧情、外部测试和返工；每阶段结束后重估剩余工作。

通用完成条件：项目可启动；当前阶段的主路径可玩；错误和失败能说明原因；固定种子可重现关键结果；相关自动化或手动验证留有记录；没有覆盖用户已有文件。

## 2. 阶段总览

| 阶段 | 重点 | 原计划粗估 | 进入条件 | 阶段出口 |
|---|---|---:|---|---|
| **P0 奠基** | 工程、数据、状态、输入、雷达 UI 骨架 | 2–3 周 | 工程初始化 | M0：雷达样例可交互，基础数据可校验 |
| **P1 垂直切片** | 搜索→交火→驾机→返航→结算 | 4–6 周 | M0；海空切换规则明确 | M1：完整单关连续可玩 |
| **P2 海战扩展** | 武器、火控、地形、损管、舰艇 AI | 6–8 周 | M1 | M2：海战取舍可观察、可复测 |
| **P3 空战扩展** | 飞行、僚机、对海攻击、着舰 | 6–8 周 | M1；可与 P2 的独立任务并行 | M3：空中行动影响海战 |
| **P4 战役基础** | 多任务、后勤、评分、复盘、存档 | 6–8 周，需重估 | M2/M3 的状态和事件稳定 | M4：连续任务有因果与一致结算 |
| **P5 成长与制造** | 技能、学说、舰机升级和组装 | 8–10 周，需重估 | M4；时代与模式边界明确 | M5：配置选择形成可解释的取舍 |
| **P6 动态战役与内容** | 中立外交、战略 AI、任务与单位内容 | 10–12 周，需重估 | M4/M5；外交规则明确 | M6：玩家行动影响后续战局 |
| **P7 打磨与发布准备** | 平衡、性能、音画、无障碍、本地化 | 6–8 周，需重估 | M6；内容范围冻结 | M7：发布候选版本通过检查 |

P4/P5 的顺序采用 `plan.md`：先让资源、评分和连续任务有稳定归属，再接入大量成长与制造数据。这与 `plan-code.md` 的原 P4/P5 顺序不同，属于执行安排，后续可根据原型结果调整。

## 3. P0 奠基：从工程初始化到 M0

### P0.0 工程初始化

- 建立 Godot 项目配置、主场景、基础目录、Git 忽略规则和启动说明。
- 主场景只显示项目已初始化的占位内容，不冒充已完成的雷达玩法。
- 建立仓库级版本控制；不配置或猜测远程地址，不创建空承诺的依赖。
- 验收：文件齐全、引用路径一致；有 Godot 可执行文件时执行编辑器导入与无窗口启动检查。

### P0.1 规则与状态设计

- 写一页单关流程：舰桥、出击配置、切换等待、座舱、返航、结算、战役失败。
- 冻结 M1 所需四项规则：继续条件、起降载具、任务胜利条件、时间/AI 接管规则。未确认前只使用可替换的原型配置。
- 定义状态转换表，列出每次转换保留或改变的玩家、舰艇、飞机、任务状态。
- 验收：所有允许和禁止的转换都有明确结果；关键异常（飞机坠毁、母舰沉没、任务完成时玩家仍在空中）有结算路径。

### P0.2 数据和事件骨架

- 定义最小数据：舰艇、飞机、武器、雷达目标和任务；每项有稳定 ID，引用能校验。
- 区分静态定义、运行时状态与存档快照；为后续数据版本留字段。
- 定义最小事件：接触发现/更新/丢失、命令下达、武器发射、伤害、模式切换、任务结算。
- 验收：错误 ID 和缺字段给出可定位日志；同一份样例数据可重复加载；没有由 UI 直接改写战斗数据的隐藏通道。

### P0.3 雷达与输入骨架

- 显示主雷达 PPI、扫描范围、己方位置、一个模拟接触及接触详情；先保证可读，再增加 CRT 视觉效果。
- 建立输入映射和焦点规则，支持鼠标选择及键盘返回/暂停。
- 验收：玩家可选择、取消选择接触；信息更新和失联有不同提示；文字与标记在目标窗口大小下清晰可辨。

## 4. P1 单关海空闭环：M1

### P1.1 固定场景与世界时钟

- 使用固定种子生成或加载一张小型群岛地图。先有可航行水域、岛屿遮挡和至少一个敌方目标。
- 明确真实时间、暂停、切换等待和 AI 更新由哪个时钟驱动。
- 验收：相同种子和相同命令序列可复测地形和关键事件。

### P1.2 海战最小交互

- 玩家控制一艘舰艇的航向、速度和一组武器；雷达接触从未知到识别有可见状态。
- 敌方能移动或还击，伤害能改变可继续作战的状态。
- 验收：玩家可通过搜索、判断和射击完成海面目标；射击失败原因可查。

### P1.3 出击与 AI 接管

- 配置一架飞机并开始切换；舰艇按明确的最后命令或安全默认行为继续运行。
- 飞机获得控制权时，玩家可查看母舰状态；回舰后恢复舰艇控制权。
- 验收：玩家离舰期间舰艇位置、伤害与任务状态持续变化；没有重复控制或冻结世界。

### P1.4 飞行、返航和结算

- 飞机具备最小移动、燃油、侦察/攻击和降落判定。
- 完成任务后显示目标、耗时、己方损失与失败原因；死亡终止当前战役原型。
- 验收：能完整跑通成功、飞机损失、舰艇损失和燃油耗尽等关键分支。

### P1.5 切片评估门

- 记录至少几轮完整游玩的操作困惑、雷达误读、等待时间和风险归因。
- 根据记录决定 P2/P3 的优先次序；未证明有用的效果和子系统保持候选状态。
- 验收：有实际游玩记录和问题清单，而非仅有代码运行结果。

## 5. P2 海战扩展：M2

- **P2.1 雷达与识别**：增益、距离档、地形杂波、接触误差和失联；目标状态不能无解释地从未知变为精确。
- **P2.2 武器与火控**：炮位/射界、装填、弹药、提前量、校射；阻挡和友军风险给出提示。
- **P2.3 损伤与损管**：火灾、进水、系统损坏、损管命令；优先实现能改变玩家选择的少量故障。
- **P2.4 海战 AI**：敌舰巡逻、搜索、攻击、规避和己方托管；建立行为日志与固定种子回放。
- **P2.5 扩展评估**：反潜、水雷、通信与电子战以单一可反制场景逐项验证，再决定完整规则。
- **出口**：至少两种战术路线能在同一场景造成不同结果；玩家能从画面和日志判断原因。

## 6. P3 空战扩展：M3

- **P3.1 飞行与座舱**：速度、高度、转向、燃油、受损反馈；控制手感先于复杂飞行参数。
- **P3.2 侦察与打击**：对海/对空目标、攻击窗口、命中与情报回传；海面态势随之更新。
- **P3.3 僚机与敌机**：少量明确命令（跟随、掩护、攻击、返航）及可解释的响应失败。
- **P3.4 返航与着舰**：可见降落条件、受损判定、失败处理；气象和甲板周期随后逐项接入。
- **出口**：侦察、攻击和保守返航各有成本与收益；失事能归因于可见条件或操作。

## 7. P4 战役基础：M4

- **P4.1 任务模型**：主任务、次任务和隐藏目标共享结算接口，但各有独立胜利条件；避免所有任务强制歼灭。
- **P4.2 后勤**：燃油、弹药、修理、港口与补给线；每项资源至少影响一项可见任务选择。
- **P4.3 评分和复盘**：按目标、损失、情报、时间、误击等维度记账；展示关键事件时间线。
- **P4.4 存档**：定义战役继续点、死亡后的不可恢复范围和版本兼容策略；不将“一命”误写成禁止保存运行状态。
- **出口**：多关连续游玩后，资源、损失和任务结果被正确继承；评分可由事件记录解释。

## 8. P5 成长与制造：M5

- **P5.1 三层成长**：硬件升级、五类技能点、单一学说分别有用途和成本；先做每层少量代表项。
- **P5.2 兼容规则**：舰体/机体槽位、重量、电力、部件等级；拒绝不兼容组合时说明原因。
- **P5.3 资源经济**：奖励、采购、制造、维修成本通过连续战役测试，避免高评分滚雪球。
- **P5.4 模式边界**：确定剧情历史舰与跨时代自由建造如何分开；之后才扩充到大量部件和 2050 概念装备。
- **出口**：两种配置产生可观察的战术差异；技能、学说、硬件叠加有边界；错误配置不损坏存档。

## 9. P6 动态战役与内容：M6

- **P6.1 中立与交战规则**：识别、误击、保护、贸易和通行权进入统一关系日志；国家层和结构层关系分别定义。
- **P6.2 战略 AI**：有限的增援、重建或目标转换先实现一种因果链，验证玩家行动能改变下一关。
- **P6.3 任务和单位内容**：按任务需求增加舰艇、飞机、武器、地形、关卡；数据复用优先于重复脚本。
- **P6.4 特殊玩法**：登陆、政治/指挥链、俘虏与搜救在基础战役稳定后按独立场景评估。
- **出口**：战役至少能展示数次由玩家选择触发的后续变化，且有记录可以追溯。

## 10. P7 打磨与发布准备：M7

- 建立目标机器和场景规模下的帧率、加载、内存基线；逐项优化雷达/CRT、多实体和地形。
- 完成声音告警、输入可改、视觉效果减弱、颜色之外的阵营识别与必要本地化。
- 固定内容范围，跑通成功/失败/存档恢复/数据升级/异常退出后的关键回归。
- 准备发布说明、已知问题和安装方式。以发布候选版本实际测试结果决定是否交付。

## 11. 风险、依赖和变更门

| 风险 | 早期验证 | 触发调整的信号 |
|---|---|---|
| 雷达与 CRT 可读性 | P0 模拟接触和 P1 玩家试用 | 玩家反复误认目标或读不出威胁 |
| 海空切换复杂度 | P1 状态转换与失败分支 | 状态不同步、托管结果不可理解 |
| 一命惩罚过重 | P1/P4 失败记录与复盘 | 死亡主要来自无法预见的信息 |
| 程序地形与 AI 组合失控 | 固定种子样例、边界地图和事件日志 | 生成不可完成关卡或复现失败 |
| 系统规模膨胀 | 每阶段仅交付其出口所需规则 | 新系统不能产生新的决策或反制 |
| 存档兼容 | P4 起保存数据版本和迁移样例 | 更新后旧战役无法读取或静默丢失 |

设计决策记录在 `docs/decisions/`；每条写明问题、备选、决定、影响范围和日期。决策未作出时，可做可逆的原型，不将临时规则写成正式玩法。阶段出口未达成时，先修复当前阶段，再扩张内容。
