# 《群岛回波 / Echoes of the Archipelago》项目总计划

状态：整合草案。本文汇总现有玩法与开发规划；标为“待定”的内容尚未视为已确定需求。

## 1. 项目目标

制作一款 Windows 桌面优先的单人群岛空海战游戏。玩家扮演一名只有一条命的指挥官，在舰桥通过 CRT 雷达搜索、识别、指挥舰队和操作武器，也能亲自驾机侦察或攻击。离开舰桥后，舰艇由 AI 按既定命令接管；返航后重新指挥海战。战役由可复现的种子地图、任务、资源消耗和战后评分串联。

游戏要反复验证的体验是：**有限情报 → 判断目标和风险 → 下达命令或亲自出击 → 承担切换代价 → 获得可解释的结果 → 调整下一步行动。**

设计支柱：

- **信息就是生命**：雷达有延迟、杂波、遮挡与欺骗；侦察和识别有价值。
- **海空是同一场战斗**：空中行动会改变海面态势，海面舰艇在玩家离开时仍持续行动。
- **一命与可归因风险**：死亡结束当前战役；重大损失应有预警、反制和复盘信息。
- **地形与时间影响决策**：岛屿、山体、浅滩、天气和出击窗口改变航线、射界与探测。
- **战役会回应玩家**：任务、资源、外交和敌方行动随结果变化；具体深度按阶段增加。

## 3. 范围与阶段边界

完整愿景包括海战、空战、程序地形、战役、外交、成长、舰船与飞机制造，以及环境、后勤、电子战、反潜、登陆等中间机制。它们保留在项目范围内，但不要求在首个可玩版本同时完成。

首个可玩版本只验证海空切换是否产生有趣的取舍。必须具备：一张种子固定的群岛地图、一艘具备合理起降条件的玩家舰艇、一架可驾驶飞机、少量敌我目标、雷达搜索与识别、基本交火、出击配置、AI 接管、返航降落、失败和结算。此处的具体单位与时代属于原型配置，不定义最终内容上限。

原型阶段暂用固定任务、基础地形、少量武器和简单 AI；外交、五线技能树、学说、制造、动态战略 AI、完整损管及大量单位在后续阶段接入。每加入一个系统，都应说明它给核心循环增加了什么决策、代价、反制和反馈。

## 4. 技术路线与系统边界

- 引擎采用 `plan-code.md` 的 Godot 4.x；主逻辑使用 GDScript。只有性能或工具收益得到验证时，再考虑局部使用 C#。
- 采用场景与模块分离：世界实体、海战、空战、UI、战役状态各自负责本领域；跨系统变化通过明确状态转换和信号传递。
- 舰船、飞机、武器、弹药、任务、AI、地形参数和学说尽量由 Godot Resource 驱动；加载时校验 ID、引用和必需字段。存档保存状态和数据版本，不把资源文件当作存档。
- 种子控制地图、任务和可复现随机事件。测试与复盘记录种子、规则版本及关键事件；实时 AI 的可复现边界在原型中确认。
- CRT 首先保证目标、距离、威胁、武器状态和告警可读；扫描线、余晖和透视效果逐步加入，并提供弱化视觉效果的选项。
- 时间控制先确定暂停、切换等待和 AI 接管期间哪些模拟继续推进；命令队列与加速在交互压力验证后扩展。
- `GameManager`、`DataManager` 等 Autoload 是全局单例，不作为 `Main` 场景的子节点重复实例化。场景结构与自动加载表分别维护。

首个需要冻结的数据接口：`EntityId`、阵营与识别状态、雷达接触、命令、武器射击事件、伤害事件、任务结果、战役状态。系统间传递事件与标识，避免 UI 直接修改战斗实体的内部状态。

## 5. 开发阶段与验收

阶段按依赖顺序推进。`plan-code.md` 的周期只作粗略估计，完成前一阶段的验收后再细化下一阶段排期。

| 阶段 | 主要交付 | 可验证的完成条件 |
|---|---|---|
| **M0 项目奠基** | Godot 项目、目录约定、输入映射、数据加载与校验、状态机骨架、可交互雷达屏。 | 能启动、加载样例数据，在雷达屏上显示并选择一个模拟接触；错误数据给出明确提示。 |
| **M1 海空垂直切片** | 固定种子群岛、舰艇移动、雷达接触、基础射击、飞机起降、AI 接管、结算与失败。 | 从舰桥搜索、交火、亲自出击、返航、再次接管舰艇到任务结算可连续完成；舰艇在离舰期间继续按规则行动。 |
| **M2 海战扩展** | 多炮位与弹药、火控和射界、地形遮挡、基本损管、敌我舰艇 AI。 | 同一场交战中，目标识别、炮位选择、地形与损管能造成可观察的不同结果；可用固定种子复测。 |
| **M3 空战扩展** | 飞行与座舱信息、僚机命令、对空与对海攻击、燃油及着舰风险。 | 空中侦察或攻击能改变海面态势；返航、受损降落和失去舰艇均有明确结算。 |
| **M4 战役基础** | 主次任务、补给与维修、关卡衔接、评分、战后复盘、存档规则。 | 连续任务会继承资源与损失；评分依据可查看；死亡、失败和继续条件一致。 |
| **M5 成长与制造** | 五类技能点、学说、硬件升级、部件兼容与制造。 | 至少两种不同配置能形成有意义的取舍；升级、技能和学说的叠加有上限与可解释效果。 |
| **M6 动态战役与内容** | 中立势力、外交、敌方战略反馈、更多地形与任务、舰机武器内容、剧情/沙盒边界。 | 玩家对中立目标和关键任务的行动能改变后续态势，变化有日志和可追溯原因。 |
| **M7 打磨与发布准备** | 平衡、性能、音效、可读性与无障碍、本地化、兼容和稳定性。 | 关键流程、存档恢复、性能目标和发布检查通过；已知限制被记录。 |

### M1 的实际工作顺序

1. 定义一关任务流程、胜败条件、玩家身份与起降地点；同时画出海战、配置、切换、飞行、返航、结算的状态图。
2. 建立数据样例与固定种子场景，先让雷达接触、目标选择和基础命令工作。
3. 接入舰艇移动、射击、伤害和最小 AI，保证玩家离舰时世界继续运行。
4. 接入出击配置、飞机控制、基础侦察/攻击与返航判定。
5. 接入任务结算和战后事件记录；用同一种子反复验证完整流程。
6. 邀请玩家测试雷达可读性、海空切换代价和死亡归因，据反馈修订 M2/M3 的范围。

## 6. 后续机制如何接入

| 机制组 | 首次适合接入的阶段 | 与核心循环的关系 |
|---|---|---|
| 昼夜、天气、海况、潮汐 | M2–M3 起逐项加入 | 改变探测、航线、起降和攻击窗口。 |
| 反潜、水雷、封锁 | M2 后 | 增加海面隐蔽威胁、护航与路线选择。 |
| 燃料、弹药、维修、运输补给 | M4 | 让单关选择影响下一关。 |
| 通信、电子战、假目标与假图 | M2–M4 | 建立探测、欺骗、识破和反制链。 |
| 完整损管、人员、搜救 | M2–M4 | 提供可归因的生存选择与失败复盘。 |
| 航母甲板周期、僚机波次 | M3 后 | 形成出击和回收的时间窗口。 |
| 登陆与地面目标 | M6 | 作为海空任务结果和少数关键节点，避免另起一套完整陆战游戏。 |
| 中立关系、交战规则、外交 | M6 | 让识别、误击、保护和贸易改变阵营关系。 |
| 动态战略 AI、政治与指挥链 | M6 后评估 | 让战役回应玩家，并处理指挥所及旗舰损失。 |
| 复盘、种子分享、继承、排行榜 | M4 起分批加入 | 支持一命失败后的学习与重玩；继承规则需单独确认。 |

## 7. 实施前需要冻结的设计决策

这些问题会改变状态机、任务数据或内容结构，应在对应阶段开始前定稿。以下是建议的讨论选项，并非已确认规则。

1. **起降与生存**：安全降落回舰是唯一继续方式，还是允许友方机场、紧急机场和搜救继续战役？舰艇沉没而玩家在空中时如何结算？M1 前确定。
2. **玩家的舰艇与机型**：舰长能从哪些舰艇出击？驱逐舰侦察机示例是否需要水上飞机、弹射器和回收规则？M1 前确定原型配置。
3. **任务胜利条件**：侦察、护航、封锁、登陆与歼灭任务各自如何成功；“摧毁敌方目标”是部分关卡目标还是所有关卡的总目标？M1 前确定任务数据模型。
4. **时间规则**：实时、可暂停、可加速如何组合；切换等待中玩家能否看情报或发命令；AI 接管的最低可靠性是什么？M1 前确定。
5. **时代与模式**：老式 CRT 战役和一战至 2050 跨时代拼装如何共存；剧情模式与自由制造模式分别允许哪些单位？M5 前确定。
6. **失败与备份**：己方指挥所被毁直接结束、备份继续，还是只影响评分和指挥效率？主角死亡与指挥链继任如何区分？M4/M6 前确定。
7. **外交关系模型**：国家层和结构层的关系怎样汇总；双向关系、阈值、误击和宣战如何进入同一套规则？M6 前确定。
8. **成长继承**：死亡清空当前战役，但哪些解锁或学说经验可以跨战役保留？M5 前确定。

## 8. 验证与变更管理

- 每阶段保留可运行版本，并记录固定种子、预期事件和实际结果。优先验证海空切换、AI 接管、任务结算、存档恢复等跨系统路径。
- 数据加载、伤害/评分计算和状态转换适合自动化测试；雷达可读性、飞行手感、决策压力需要实际游玩验证。性能指标在有可运行场景后建立基线。
- 每次加入机制先写清输入、状态变化、玩家反馈、失败处理和最小验收，再实施。无法解释其对核心循环的作用时，留在扩充清单。
- 遵循项目开发规范保护已有文件；改动前检查现状，改动后进行适当验证并审查差异。不以文档中的估计周期或功能清单代替验收。
